Section 1 · ~15 min

1 · Architecture Overview Beginner

One mental picture explains the whole deployment. You build on a Developer PC, package everything into an MTAR archive, push it to SAP BTP Cloud Foundry, where two modules come alive: the Node.js CAP service (bookshop-srv) and the HDI deployer (bookshop-db-deployer). Both talk to the same HDI container inside SAP HANA Cloud.

flowchart TD
  PC["Developer PC
npm install / cds build / mbt build"] --> MTAR["MTAR archive
bookshop_1.0.0.mtar"]
  MTAR --> CF["SAP BTP Cloud Foundry
org + space"]
  CF --> SRV["bookshop-srv
Node.js CAP runtime"]
  CF --> DEP["bookshop-db-deployer
HDI deployment"]
  SRV --> HDI[("HDI Container
isolated schema set")]
  DEP --> HDI
  HDI --> HANA[("SAP HANA Cloud
managed database")]
  CFR["Cloud Foundry Router
public HTTPS route"] --> SRV
  SRV --> API["CAP OData APIs
/odata/v4/..."]
  API --> HDI
Developer PCWindows + PowerShell. Node.js, CDS CLI, MBT, CF CLI installed here. Builds the MTAR; never hosts production data.
MTARMulti-Target Archive: versioned package of all modules + resource descriptors. The single artifact CF deploys.
bookshop-srvNode.js module serving OData V4. Gets HANA credentials injected via service binding — never hardcoded.
bookshop-db-deployerShort-lived HDI deployer. Creates tables/views in the HDI container, then stops. Re-runs on every deploy.
HDI ContainerIsolated schema +di container inside HANA Cloud. Your tables live here, separated from other apps.
CF Router + RoutePublic HTTPS entry point, e.g. https://bookshop-srv.cfapps.<REGION>.hana.ondemand.com. Created automatically at deploy.
Real-world read: traffic flows Router → bookshop-srv → HDI container → HANA Cloud. The deployer only runs at deploy time; at runtime only srv and the container matter.
Target project: bookshop/ with app/, db/schema.cds, srv/catalog-service.cds, srv/admin-service.cds, srv/orders-service.cds, package.json, mta.yaml. Your exact files may differ — the deployment mechanics are identical for any CAP app.

5 · Verify Cloud Foundry Quota Advanced

Why this section is ★ critical: a deployment can fail even when the project is 100% correct if the org lacks quota — memory, instances, routes or service instances. Check quota before you build.
cf org <ORG>
cf spaces
cf apps
cf routes
cf quotas
cf space-quota
Quota dimensionWhat it capsTypical failure signal
Application memorySum of RAM across app instances.Application memory quota exceeded
InstancesTotal running app instances.Scale/start rejected.
RoutesTotal hostnames bound in the organization.Routes quota exceeded for organization
Service instancesNumber of provisioned services (HDI, HANA…).Service quota exceeded
Routes trap: cf routes shows routes in your current space only. Seeing "No routes found" there does NOT mean the org has free route quota — other spaces in the same org may consume it all. Always check the org-level quota, not just your space.

Inspect the org through the CF v3 API — get the org GUID, then its quota GUID:

cf curl "/v3/organizations?names=<ORG_NAME>"
# from the JSON, note: guid = organization GUID,
# relationships.quota.data.guid = quota GUID

cf curl /v3/organization_quotas/<QUOTA_GUID>
Quota JSON fieldMeaning
apps.total_memory_in_mbMax RAM across all apps in the org.
apps.total_instancesMax app instances in the org.
routes.total_routesMax routes in the org (all spaces combined).
services.total_service_instancesMax provisioned service instances.

Section 6 · ~15 min

6 · HANA Cloud vs HDI Container Intermediate

Two different things with similar names. Confusing them causes most HANA setup mistakes:

flowchart TD
  HC["SAP HANA Cloud
managed database service"] --> DB["HANA Database
your data instance"]
  DB --> HDI[("HDI Container
isolated design-time box")]
  HDI --> CAP["CAP application
binds to container, not DB"]
SAP HANA Cloud databaseCloud Foundry HDI container
The managed database service/instance (compute + storage).An isolated schema container inside that database for one app.
Shared platform capability, created once.Created per application (bookshop-db), versioned with it.
Administered in BTP Cockpit / HANA Cockpit.Deployed by the bookshop-db-deployer module on every cf deploy.
Why CAP uses an HDI container: design-time CDS artifacts deploy as versioned HDI objects (tables, views, procedures) with dependency tracking and safe redeploys — instead of hand-created tables in a shared schema. Each app gets isolation, repeatable deploys and clean undeploys.

Check what the marketplace offers in your landscape (plans vary):

cf marketplace -e hana-cloud

Typical trial plans you may see: hana-free, hana-cloud-connection-free. Exact names depend on entitlements — use what your marketplace lists.

10 · Database Layer — db/schema.cds Intermediate

Simplest shape (from the brief) vs this project's real model (richer — Genres, Authors, Books, Reviews, Customers, Orders, OrderItems with cuid, managed aspects and associations):

namespace sap.capire.bookshop;

entity Books {
  key ID : Integer;
  title  : String(100);
  author : String(100);
  price  : Decimal(9,2);
}

Your namespace, keys (cuid vs Integer) and fields will differ — the pipeline below is the same. During cds build --production:

flowchart LR
  CDS["CDS model
db/schema.cds"] --> CSN["CSN
compiled model"]
  CSN --> HANA["HANA artifacts
hdbtable / hdbview / ..."]
  HANA --> HDI[("HDI deploy
into container")]
Key insight: you never write .hdbtable files by hand. CDS is the single source of truth; the compiler derives correct, dependency-ordered HANA artifacts, and the deployer applies them idempotently.
Section 11 · ~15 min

11 · Service Layer — srv/*.cds Intermediate

using { sap.capire.bookshop as my } from '../db/schema';

service CatalogService {
  entity Books as projection on my.Books;
}
ConceptMeaning
projectionExposes a shaped view of a persistence entity — subset of fields, renamed, access-controlled — without duplicating the table. This project exposes e.g. bahi as projection on my.Books plus lekhaka, Genres, Reviews, Customers, Orders, computed entities, actions and functions.
OData exposureEach service becomes an OData V4 endpoint (/odata/v4/catalog/…, /odata/v4/admin, /odata/v4/orders). Entities → entity sets; actions/functions → operations.
Remember: db/ defines what is stored; srv/ defines what is served. Deploy problems in §21 split cleanly along this line: deployer failures = db/; 404/empty OData = srv/.

12 · mta.yaml Deep Dive Intermediate

The exact mta.yaml of this bookshop (the deploy contract — read it line by line):

_schema-version: 3.3.0
ID: bookshop
version: 1.0.0
description: "CAP Bookshop Application"

parameters:
  enable-parallel-deployments: true

build-parameters:
  before-all:
    - builder: custom
      commands:
        - npm ci
        - npx cds build --production

modules:

  # CAP Application
  - name: bookshop-srv
    type: nodejs
    path: gen/srv
    parameters:
      instances: 1
      buildpack: nodejs_buildpack
    build-parameters:
      builder: npm
    provides:
      - name: srv-api
        properties:
          srv-url: ${default-url}
    requires:
      - name: bookshop-db

  # HANA Database Deployer
  - name: bookshop-db-deployer
    type: hdb
    path: gen/db
    parameters:
      buildpack: nodejs_buildpack
    requires:
      - name: bookshop-db

resources:

  # HANA HDI Container
  - name: bookshop-db
    type: com.sap.xs.hdi-container
    parameters:
      service: hana
      service-plan: hdi-shared
PropertyMeaningWhy it matters
ID / versionApp identity + version → MTAR filename bookshop_1.0.0.mtar.Bump version per release; CF tracks deployment history by it.
modulesDeployable units: bookshop-srv + bookshop-db-deployer.Two lifecycles: long-running app vs run-once deployer.
resourcesService instances CF must provision: bookshop-db HDI container.Missing resource = binding failure at staging.
typenodejs = CF app; hdb = HDI deployer task.Wrong type = wrong buildpack behavior.
pathBuild output consumed: gen/srv, gen/db.Must match cds build --production output. Wrong path = empty module.
requiresService binding wiring (srv → container; deployer → container).How credentials get injected — no hardcoded passwords.
providesExposes srv-url: ${default-url} for downstream consumers (approuter).Needed once you add App Router / destinations later.
build-parameters / before-allnpm ci then cds build --production before every module build.Guarantees gen/ exists and is reproducible (npm ci uses the lockfile).
buildercustom (shell commands) and npm (module packaging).Custom = your commands; npm = standard Node packaging.
buildpacknodejs_buildpack stages and runs the code.Pin/verify against what your foundation supports.
service / service-planhana : hdi-shared — which backing service to provision.Must be entitled in your subaccount or provisioning fails.
Do NOT "fix" deploy errors by randomly editing types, paths or plans. 90% of mta.yaml failures are stale gen/ output or missing quota/entitlement — rebuild cleanly first (§13–14) before touching this file.
Section 13 · ~15 min · ★ core

13 · cds build --production Intermediate

Use exactly: cds build --production — NOT npx cds build --production, unless this project specifically requires it. (This bookshop's mta.yaml uses npx in its before-all hook; run the plain form yourself in PowerShell so you use the project's installed CLI consistently.) npx can silently fetch a different compiler version than your locked toolchain, producing artifacts your dependencies don't understand.
cd <project>
npm install
cds build --production

Generated output:

bookshop/
├── gen/
│   ├── db/        # compiled HANA artifacts → bookshop-db-deployer (path: gen/db)
│   └── srv/       # staged Node.js service → bookshop-srv (path: gen/srv)
├── mta_archives/  # created later by mbt build
Rule of thumb: if gen/ is stale or suspect, delete it and rebuild. Never hand-edit files inside gen/ — they are compiler output.

Section 21 · ~40 min · ★ reference

21 · Common Errors — All 15 Decoded Advanced

1 · Routes quota exceeded Advanced

Error: Routes quota exceeded for organization

Meaning: org-level route quota exhausted across ALL spaces.

Diagnose: cf routes (all spaces) · cf curl /v3/organization_quotas/<GUID> → routes.total_routes.

Solution: delete unused routes (cf delete-route), remove stale apps, or request more quota. Do NOT recreate the space hoping quota follows — it is org-scoped.

2 · Application memory quota exceeded Advanced

Error: staging/start rejected on memory.

Diagnose: cf org <ORG> · compare apps.total_memory_in_mb used vs limit; cf app <APP> shows requested RAM.

Solution: stop unused apps, lower requested memory, or raise quota. Do NOT shrink memory below what Node.js needs to stage.

3 · No space quota Intermediate

Error: deploy blocked referencing the space quota.

Diagnose: cf space-quota · cf space <SPACE>.

Solution: target a space with quota or ask the org manager to adjust the space quota. Do NOT edit mta.yaml memory to dodge it blindly.

4 · Service quota exceeded Advanced

Error: new HDI/HANA instance refused.

Diagnose: cf services count vs services.total_service_instances.

Solution: reuse the existing container, delete orphans, or raise quota. Do NOT create duplicate containers per retry.

5 · HANA service creation failed Intermediate

Error: cf service <DB> shows failed.

Diagnose: read the service message; verify entitlement/region/plan via cf marketplace -e hana-cloud.

Solution: pick an entitled plan+region, delete the failed instance, recreate. Do NOT proceed to HDI creation first.

6 · HDI deployer failed Intermediate

Error: bookshop-db-deployer exits non-zero; tables missing.

Diagnose: deploy task logs · cf logs · check gen/db exists and is fresh.

Solution: clean rebuild (cds build --production), fix CDS compile errors, redeploy. Do NOT hand-create the missing tables.

7 · npm ci failed Beginner

Error: lockfile/registry failure in before-all.

Diagnose: run npm ci locally in PowerShell; read the first error (network? lockfile out of sync?).

Solution: npm install to refresh the lockfile, commit it, rebuild. Do NOT delete the lockfile to "fix" it.

8 · ERESOLVE dependency error Intermediate

Error: peer-dependency conflict during install.

Diagnose: note the conflicting packages in the log; check @sap/cds vs @cap-js/* version matrix.

Solution: align versions deliberately (upgrade the lagging package). Do NOT ship --legacy-peer-deps as the permanent fix.

9 · cds build failed Intermediate

Error: compiler rejects the model.

Diagnose: run cds build --production alone; fix the first CDS error top-down.

Solution: correct db//srv/ syntax, rebuild, then mbt build. Do NOT deploy the previous MTAR "to test".

10 · mbt build failed Intermediate

Error: MBT aborts before producing an MTAR.

Diagnose: validate mta.yaml (indentation, paths gen/srv + gen/db), confirm gen/ was built.

Solution: fix descriptor/build order, rebuild. Do NOT zip modules manually.

11 · MTAR deployment failed Advanced

Error: cf deploy aborts mid-operation.

Diagnose: note the operation ID; inspect which stage (§15) aborted + its log.

Solution: fix the stage cause, then cf deploy -i <OP_ID> -a retry or -a abort. Do NOT fire a fresh deploy over a half-applied one.

12 · 503 Service Unavailable Intermediate

Error: route exists but returns 503.

Diagnose: cf apps (is it RUNNING?) · cf logs <APP> --recent · check route→app mapping.

Solution: start/fix the app, remap route if needed. Do NOT assume a DNS problem first.

13 · Application crashes on start Intermediate

Error: CRASHED / restart loop.

Diagnose: cf logs <APP> --recent + cf events <APP>; look for missing prod deps or binding errors.

Solution: promote missing deps to dependencies, fix binding names, restage. Do NOT raise memory as the first fix.

14 · App starts but route doesn't work Intermediate

Error: RUNNING app, dead URL.

Diagnose: cf routes + cf app <APP> — is the route actually bound? Correct path (/odata/v4/…)?

Solution: map the route, correct the path/service name. Do NOT rebuild the MTAR for a routing issue.

15 · Destination errors Advanced

Error: calls to external S/4HANA/REST backends fail (only when destinations are configured).

Diagnose: destination service instance + binding, connectivity, certificates, proxy settings.

Solution: fix the destination definition/binding, not the CAP code. Do NOT add Destination/XSUAA services unless the app requires them.

Section 28 · ~15 min · ★ concept

28 · Why Not Connect Directly to HANA? Intermediate

flowchart TD
  HC["HANA Cloud
Database"] --> HDI[("HDI Container")]
  HDI --> DEP["CAP DB module
db-deployer"]
  DEP --> SRV["CAP Service
bookshop-srv"]
  SRV --> API["OData API
only public surface"]

A hardcoded username/password connection would leak credentials into code, bypass container isolation and versioning, break on every credential rotation, and expose raw SQL to the internet. Instead, Cloud Foundry service bindings inject per-instance credentials as environment (VCAP_SERVICES); the CAP runtime reads them via @sap/xsenv/cds env resolution. Credentials rotate without code changes, each app sees only its container, and the only public surface is the OData API.

Interview-ready sentence: the app never knows a password — the platform binds a container-scoped credential set into its environment, and HDI versioning keeps schema changes repeatable.
